---
name: i18n
description: Add a pot file and translations for the mu-plugin and theme.
---

Regenerate and update WordPress translation files (.pot/.po/.mo) for this project's theme and mu-plugin using WP-CLI, and draft translations for new strings. Use whenever the user asks to update translations, regenerate the pot file, sync po files, add missing translations, run Poedit-equivalent work, or mentions gettext, i18n, l10n, .pot, .po, or .mo files — even without naming WP-CLI explicitly.

This project has two separate translation domains, and both need to stay in sync independently — don't run one command against both at once.

Theme (Sage) — textdomain sage, unless the theme's style.css Text Domain: header says otherwise (verify, don't assume — some projects rename it).
Custom mu-plugin — textdomain project-name in this project. If working in a different project, confirm the actual textdomain from the plugin's main file header or its load_muplugin_textdomain() call rather than reusing this one — mu-plugin textdomains are typically client-specific, not a fixed convention across projects.

Default target locale is nl_NL unless ./deploy.php defines more languages.

Locate the languages folder for each domain

Check for an existing languages/ directory inside the theme root and the mu-plugin's own directory first — most Bedrock/Sage projects put it there (web/app/themes/project-name/languages/, web/app/mu-plugins/project-name/languages/), but some Sage setups use resources/lang instead. Use whatever location the existing .pot/.po files are already in rather than creating a second one in the "standard" location — that just splits the translations across two places.

Update one domain

Run these three in sequence for a given domain (theme or mu-plugin), with <source> the theme/plugin root, <lang-dir> its languages folder, and <domain> its textdomain:

bash

# 1. Regenerate the template from the current source code

wp i18n make-pot <source> <lang-dir>/<domain>.pot \
 --domain=<domain> \
 --exclude=vendor,node_modules,dist,build,public/build

# 2. Merge new/changed strings into the existing .po file(s), preserving

# translations that are still valid. Strings whose source text changed

# get marked "fuzzy" for review; brand-new strings get an empty msgstr.

wp i18n update-po <lang-dir>/<domain>.pot <lang-dir>

# 3. Compile the updated .po files back to the binary .mo WordPress loads

wp i18n make-mo <lang-dir>

--exclude matters: without it, make-pot will scan built/minified JS in public/build (or wherever Vite/Bud output lands) and pull in garbage strings from bundled vendor code. Check the theme's build output directory if it isn't public/build and adjust.

If the theme or mu-plugin has translatable strings in JS (block editor components, etc.), also run wp i18n make-json <lang-dir> --no-purge after step 3 to split those into per-locale JSON files.

Filling in new/fuzzy strings

After update-po, open the .po file and look for entries with an empty msgstr "" or a #, fuzzy flag above them — those are what actually changed. Offer to draft the nl_NL translation for each rather than leaving them for the user to type from scratch, but treat these as a first draft: check a few already-translated entries in the same file first for the tone/formality the site already uses (formal "u" vs informal "je" in Dutch is a real, visible choice — match whatever's already there) and flag the draft as needing a native-speaker or client review before shipping, since gettext has no way to signal "unreviewed" other than you saying so.

Never guess at strings that carry legal or pricing meaning (checkout copy, terms, refund policy wording) — translate those too, but call out explicitly that they need sign-off.

Compiled files and version control

Check whether .mo (and .json, if generated) files are committed or gitignored in this project before assuming either way — some setups compile translations as part of the deploy build rather than committing binaries. Follow whatever the existing .gitignore / repo history already does.
